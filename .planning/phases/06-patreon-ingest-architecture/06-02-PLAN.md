<objective>
Replace the per-post `npx --yes patreon-dl@3.6.0` subprocess with the library's programmatic API, move the session cookie out of argv and out of the working directory, and classify download failures into actionable reasons.

Purpose: `downloadPost` currently spawns `npx` per post with the live session cookie as a command-line argument — readable by any local process via `ps` or `/proc/<pid>/cmdline`. The package is absent from `package.json`, so `--yes` resolves and installs it from the network at runtime, outside the lockfile the rest of the project maintains. And the cookie lives at `process.cwd()/.patreon-session`, so authentication appears to vanish depending on which directory the MCP client launched the server from, and can be written into whatever git repo the user happens to be in.
Output: An in-process downloader with pinned dependencies, keychain-adjacent cookie storage, and typed errors that let callers distinguish "re-authenticate" from "you are not in this tier".
</objective>

<task type="auto">
  <name>Task 4: Classify download failures</name>
  <files>src/sources/premium/patreon-errors.ts, src/sources/premium/patreon-dl.ts, src/sources/premium/__tests__/patreon-errors.test.ts</files>
  <action>Create `patreon-errors.ts` exporting `type PatreonErrorReason = 'cookie-expired' | 'not-entitled' | 'not-found' | 'network' | 'unknown'` and `classifyDownloadError(error: unknown): { reason: PatreonErrorReason; message: string; actionable: boolean }`.

  **Classify on error context, not on bare HTTP status.** patreon-dl surfaces `FetcherError` carrying the request target, and a 403 can come from an embedded media host (`stream.mux.com` and similar) rather than from Patreon auth or entitlement. A status-only mapping turns one failed video fetch into `cookie-expired`, which under 06-04's rules aborts the entire sync. Establish precedence explicitly: a 401/403 whose target host is Patreon itself maps to `cookie-expired` (401) or `not-entitled` (403); a 403 from any other host is a per-asset `network` failure that must not escalate; 404 is `not-found`; transport-level failures are `network`; anything unrecognised is `unknown`. Widen the `downloadPost` result to `{ success: boolean; files?: DownloadedFile[]; error?: string; reason?: PatreonErrorReason }` and populate `reason` on every failure path. Route the messages through the existing `logError` helper so credential-bearing strings stay sanitized. This plan only produces the classification — surfacing it to users is 06-05.</action>
  <verify>npm test -- src/sources/premium/__tests__/patreon-errors.test.ts src/sources/premium/__tests__/patreon-dl.test.ts</verify>
  <done>Each reason is produced by a representative error input — expired cookie (Patreon 401), inaccessible post (Patreon 403), embedded-host 403, 404, and transport failure — the embedded-host case does **not** classify as `cookie-expired`, and no failure path returns a bare stringified exception.</done>
