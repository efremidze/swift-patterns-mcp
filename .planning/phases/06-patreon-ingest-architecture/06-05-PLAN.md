<objective>
Invert the dependency so Patreon is the content source of record and YouTube is optional metadata: enumerate campaign posts directly, match them to videos by similarity rather than by link presence, and drive the creator list from the user's real memberships.

Purpose: enrichment only fires for URLs matching `patreon.com/posts/`, but most creators put a *campaign* link in their video descriptions, not a per-post one. For those videos nothing is ever downloaded and the returned "Patreon pattern" is a YouTube description wearing a Patreon URL — the headline capability quietly no-ops on most of its inputs. Meanwhile `CREATORS` pins the tool to exactly three creators even though `getSubscribedCreators()` already computes the user's actual active memberships and the search path ignores the result.
Output: Discovery that does not depend on creators linking posts in free text, and a tool that works for whoever the user actually supports.
</objective>

Persist the resolved list to `~/.swift-patterns-mcp/creators.json` at sync time so the query path and CLI can read it without an OAuth round-trip, and let a user-maintained `youtubeChannelId` override in that file survive refreshes. `patreon-sync.ts` iterates the resolved list rather than `withYouTube()`.

  Keep three states distinct — a successful lookup that finds nothing is **not** the same as a lookup that could not run:

  | State | Condition | Resolved creators |
  |---|---|---|
  | `membership` | OAuth succeeded, payload well-formed, >=1 Swift campaign | those campaigns |
  | `membership-empty` | OAuth succeeded, payload well-formed, 0 Swift campaigns | **empty set** |
  | `fallback` | OAuth unconfigured, request failed, or payload missing/malformed | built-in table |

  Falling back on `membership-empty` would sync creators the user does not support, which contradicts ING-08 and guarantees a run of `not-entitled` download failures. Treat a missing or malformed `included` array as `fallback`, never as an authoritative empty result. Surface the active state through the `creators` field of the shared `PatreonStatus` payload defined in 06-04 Task 4 — do not edit `src/cli/patreon.ts` in this plan, which is why it is absent from `files_modified`.</action>

  <done>Sync covers every Swift-related campaign the user actively supports; a successful lookup with zero Swift campaigns resolves to an empty set and reports `membership-empty`; only an unavailable or malformed lookup falls back to the built-in table; and each of the three states is asserted by a test.</done>

<task type="auto">
  <name>Task 2: Enumerate campaign posts directly</name>
  <files>src/sources/premium/patreon-sync.ts</files>
  <action>Replace the discover stage's "scrape `posts/` URLs out of video descriptions" with direct campaign enumeration via the patreon-dl library's by-user/by-campaign listing (06-02), bounded by `PATREON_SYNC_MAX_POSTS_PER_CREATOR` (default 50 per run, newest first).

  **Persist a per-campaign listing cursor** at `getSwiftMcpDir()/sync-cursors.json` as `{ [campaignId]: { cursor, lastAdvancedAt, complete } }`. Without one, "newest 50" means every sync re-walks the same newest 50 and posts beyond the first page are permanently undiscoverable — `hasPost` dedupes *downloads*, not *enumeration*, so the back catalog would never be reached. Each run resumes from the stored cursor, advances it as pages are consumed, and sets `complete` when the listing is exhausted; a completed campaign re-checks only the newest page on later runs. Reset a cursor when its campaign leaves the resolved creator set, and on an explicit `--full`.

  Keep description-scraped post URLs as an additional input merged by post ID, but **resolve each one to a campaign in the resolved creator set before enqueueing it, and discard it otherwise**. A video description can link another creator's post or an unrelated Patreon post; enqueueing those reintroduces exactly the unscoped downloads that membership-derived scoping exists to prevent, and each one costs a guaranteed `not-entitled` failure.</action>

  <done>Discovery finds posts for a campaign whose videos contain only a bare campaign link; repeated syncs discover posts beyond the first page via the persisted cursor; a scraped link to a campaign outside the resolved set is discarded rather than enqueued; and link-derived and enumerated posts merge without duplication.</done>

The asymmetry decides it: keeping `campaigns` costs one extra line on the consent screen, dropping it risks the feature.
